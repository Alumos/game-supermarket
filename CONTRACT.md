# Integration contract

Use plain ES modules, browser Canvas/DOM/SVG, Node.js 24 built-ins and node:sqlite. No npm installation. All project files live inside game-supermarket. No changes to old game/data.

## Shared engine (shared/engine.mjs)
Export TASKS, CHAPTERS, DELIVERY_MAP, DELIVERY_RULES_VERSION, deliveryRulesVersion(value), initialState(chapterId,taskId,rulesVersion=DELIVERY_RULES_VERSION), availableActions(chapterId,taskId), validateGraph(graph), simulate(graph,options={chapterId,taskId}), exampleGraph(chapterId,taskId,variant), buildGraph(actions,options), deliveryPathBetween(from,to), deliveryPointId(point), actionLabel(action), normalizeDeliveryGraph(graph), normalizeDeliveryResult(result,graph). Legacy STOCK_MAP and pathBetween remain exported for historical records; stocking is not a current task. Delivery labels include the public point letter when coordinates match W/A–I, e.g. `移动到 E（10，11）`; unnamed road coordinates retain numeric labels.

Graph shape: {schemaVersion:1,chapterId:number,taskId:string,contentVersion:"1.0.0",revision:number,nodes:[{id,kind:"start"|"action"|"end",actionId?,params?,label?,x?,y?}],edges:[{from,to}]}. New delivery graphs add deliveryCoordinates:"cartesian-y-up" and deliveryRulesVersion:"split-cold-v2". deliveryRulesVersion reads graph/run/result metadata and defaults unmarked history to "left-cold-v1". buildGraph and new student drafts use the current rules. Loading/restoring an old draft upgrades only that working copy; saved run graphs/results remain immutable. simulate uses the graph rules, including the preserved legacy order definitions. Comparison and best-score selection only combine runs with matching delivery rules. normalizeDeliveryGraph returns a converted copy for legacy delivery graphs without the coordinate marker (new y=14-old y); validateGraph/simulate apply this compatibility conversion. normalizeDeliveryResult converts legacy result/trace geometry on a display copy without changing stored history or mirroring an already converted result. Delivery is displayed as Scratch-style coordinate blocks; its persisted graph remains a single chain with automatic edges. validateGraph permits 48 total nodes for delivery, 24 for other tasks. All edges must form one start-to-end chain, with no branching or cycles.

Each TASKS entry: {id,chapterId,name,npc,description,goal,actions:[{actionId,label,params?}],...}; CHAPTERS: {id,title,subtitle,story,outro}. Chapter defaults: 1 drink-swap, 2 fresh-juice, 3 tea, 4 delivery. Chapter 3 includes rice-roll, tea, plant and fish.

Action IDs:
- Chapter 1 move_crate params {from:"A",to:"C"}.
- Chapter 2 fresh-juice: wash_orange → peel_cut → add_orange → start_juicer → pack_juice, labels 清洗橙子 → 去皮切块 → 放入橙肉 → 启动机器榨汁 → 打包饮品. Loading must precede starting the juicer; each step requires the previous step.
- Chapter 3 rice-roll: seaweed,rice,filling,roll,pack; tea: cup,water,steep,remove_bag,lid; plant: soil,plant,fill,water_plant,label_plant; fish: fishfood,open_feed,feed,close_feed,record_feed. Plant's last two steps may swap. Fish's first two and last two may swap, with feed requiring both initial steps.
- Chapter 4 delivery: move_to params {x:integer,y:integer}. A block walks a continuous horizontal or vertical road only. Students add intermediate coordinates at turns. Diagonal moves, off-road targets and straight lines through buildings return useful errors and leave the successful prefix untouched. No teleportation or implicit turn routing during programmed moves.

validateGraph => {ok,errors:[{nodeId?,message,code?}],order:[nodeIds]}.
simulate => {ok,completed,errors:[],trace:[{nodeId,actionId,params,label,before,after,events:[...],duration:number,cumulative:number}],initialState,finalState,metrics:{walk:number,handling:number,total:number,onTime:boolean,coins?:number,delivered?:number,failed?:number},errorNodeId?,message}. Incorrect inputs, graph structure and state preconditions return errors as data. Source graph and frozen definitions are not mutated.

State common: {chapterId,taskId,position:{x,y},...}; drink: {slots:{A:"orange",B:"milk",C:null},holding:null}; production: {flags:{}}. Production scene work points: fresh-juice(10,9); rice-roll(3,9), tea(8,9), plant(13,9), fish(18,9).

DELIVERY_MAP:
- {width:21,height:16,coordinateMaxY:14,coordinateSystem:"cartesian-y-up",timeUnit:"minutes",points,links,orders,minutesPerCell:1,handlingMinutes:2,bonusEveryMinutes:4}.
- points: W(10,1), J0(10,3), J1(4,3), J2(16,3), A(4,7), B(10,7), C(16,7), D(4,11), E(10,11), F(16,11), G(4,3), H(10,3), I(16,3). G/H/I are public aliases of J1/J0/J2 at the left/center/right of the bottom road and can be dragged from coordinate cards. Logical coordinates increase upward; rendering maps screen y using coordinateMaxY-y. J names are internal road geometry only and are hidden from the map and student toolbox.
- links: [["W","J0"],["J1","J0"],["J0","J2"],["A","B"],["B","C"],["D","E"],["E","F"],["J1","A"],["A","D"],["J0","B"],["B","E"],["J2","C"],["C","F"]]. Every integer cell along a link is road. The grid includes several alternative routes and loops.
- orders is an array of {id,name,point,cold,deadline,baseReward,penalty}. IDs order-a through order-f correspond to A–F. A 鲜奶订单 and E 酸奶订单 are cold; both deadlines are 26, with baseReward/penalty 18. B 文具订单, C 纸巾订单, D 饼干订单 and F 水果订单 have deadlines 50,66,56,62 and baseReward/penalty 12. The legacy left-cold-v1 config retains A16/D24 cold, E58 ordinary and the original rewards for historical replay.
- deliveryPathBetween accepts a named point or {x,y} at either endpoint and returns an adjacent-cell BFS shortest path, including both endpoints, or [] for invalid endpoints. This is for map exploration and route analysis; it may turn. It does not override move_to straight-line restrictions.

Delivery state: {chapterId:4,taskId:"delivery",deliveryCoordinates:"cartesian-y-up",deliveryRulesVersion:"split-cold-v2"|"left-cold-v1",timeUnit:"minutes",position,orders:[...orderDefinition,status:"pending"|"delivered"|"spoiled",arrivedAt:null|number],coins:0,elapsed:0}. Pending orders remain pending until an actual visit, even after their deadline. Arrival at or passage through an address automatically processes its pending order exactly once. arrivedAt records simulated arrival before handling. Arrival <= deadline is delivered; later arrival is spoiled. Each delivery, successful or spoiled, adds 2 task minutes. Earlier deliveries therefore affect later arrival times. Successful reward = baseReward + floor((deadline-arrivedAt)/4); spoiled reward = -penalty. There is no initial coin allowance or zero-floor clamp.

Delivery result/state timeUnit is "minutes"; durations, cumulative, elapsed, deadlines and arrivedAt use simulated minutes for delivery, while the first three chapters still use seconds. Animation playback remains accelerated and does not multiply duration by 60. Legacy time constant aliases may remain for compatibility. Delivery results and all delivery state snapshots carry deliveryRulesVersion; normalizeDeliveryResult adds missing legacy rule metadata only on a display/verification copy, allowing old offline traces to validate without rewriting them. Delivery metrics always include {walk,handling,total,onTime,coins,delivered,failed}; total=walk+handling=state.elapsed, delivered/failed are counts, and onTime means all six delivered without spoilage. All six orders processed means ok=true and completed=true, including runs with spoiled orders, so completed runs can be compared. Reaching end while any order is pending is a GOAL failure, preserving prefix trace and metrics. There is no required return to W. Simulation uses route time only; thinking, wall time, pauses and animation speed never affect scores.

Events: existing take/place/action shapes remain. Every event includes its resulting isolated state snapshot. Delivery walks split at every automatically delivered address: {type:"walk",actionId:"move_to",from,to,path:[{x,y}],duration,state}; its snapshot is the arrival state before handling. Delivery event: {type:"delivery",actionId:"move_to",orderId,point,status,arrivedAt,coins,reward,duration:2,state}; coins and reward both mean the signed reward for this order, while state.coins is cumulative. UI may animate each walk and then apply each delivery snapshot to update orders, elapsed time and coins. Each row.duration is the sum of event durations; cumulative equals simulated elapsed time.

exampleGraph(4,"delivery","best") routes W→H→B→E→D→A→B→C→F: walk36 + handling12 = 48 minutes, 6 delivered, 0 failed, 117 coins. "good"/"demo" take W→H→G→A→D→E→B→C→F: also 48 minutes and 6 delivered, with 110 coins. Student demos use this basic example rather than the best solution. "bad"/"cross"/"reverse"/"alternate" instead take W→H→B→E→F→C→B→A→D: same 48 minutes, 5 delivered, A spoiled, 84 coins. The shorter perimeter W→H→B→A→D→E→F→C takes 44 minutes but spoils E and earns 83 coins under the current rules; the identical unmarked legacy graph retains its original 115 coins and six successes. Tests enumerate all 720 first-visit orders using optimistic shortest distances, establishing a global 117-coin upper bound and a 48-minute lower bound for routes attaining that reward; the best example achieves both. Legacy stock paths remain independent of delivery roads.

## HTTP backend and teacher UI (server.mjs, public/teacher.*)
Port default8790. Serve public/* root, shared/* under /shared/. Start with node server.mjs. Data in data/supermarket.sqlite. Nonempty SUPERMARKET_TEACHER_PASSWORD overrides the persisted teacher key, including for existing data volumes, without printing the configured password. Empty configuration retains data/teacher-key.txt; startup logs describe the credential source without printing credentials. Changing the effective credential invalidates old teacher authentication.
Teacher login POST /api/teacher/login {key}; cookie-auth. GET/POST /api/sessions {name}; list/create response {sessions,currentSessionId} / {session:{id,name,code,chapterId,phase,version,...},joinUrl}. GET /api/sessions/:id/state => {session,currentSessionId,learner?,assignment?,learners?} (teacher has learners). GET /api/student/current publicly returns {session:{id,name,chapterId,phase,version}|null}. POST /api/student/auto-join {deviceToken} returns {session,learner,assignment,currentSessionId}, or {session:null,learner:null} without an active classroom. The browser persists a random deviceToken (32–256 base64url characters), which the server hashes and never exposes in learner records. Auto-join allocates a unique per-session autoCode such as A1 (with seat/name compatibility) or reuses the browser identity in that classroom; no classroom code, seat or name required. Legacy POST /api/student/join {code,seat,name} remains compatible. Student cookie identifies browser membership; reload reuses the same current-session learner. POST /api/sessions/:id/commands {commandId,expectedVersion,action:"set-current"|"practice"|"pause"|"resume"|"next"|"chapter"|"end",chapterId?} => {session,currentSessionId}. Creating a session or set-current/practice/chapter/next/resume makes it the current admission classroom. Ending or deleting the current session clears admission; never fall back to an older session. Teacher state/SSE includes currentSessionId and updates across classrooms. phase waiting|explain|practice|paused|ended. SSE GET /api/sessions/:id/stream emits event "state" data same shape as state endpoint; teacher additionally receives event "works". Each participant fetches latest state after reconnect.
PUT /api/student/drafts/:id {graph,baseRevision,mutationId} => {draft:{id,revision,graph,...},conflict?}; use stable draft id per learner/chapter/task, conflict409 includes current saved draft, old conflicting graph retained. GET /api/student/works => {drafts,runs,submissions,feedback}. POST /api/student/runs {runId,draftId,revision,graph,status:"completed"|"failed"|"stopped"|"interrupted",executedNodes:[],trace?,offline?,reason?} => {run}. Server simulate to validate; completed only if trace nodes cover graph and goal. POST /api/student/submissions {submissionId,draftId,revision,runId?,selfAssessment?:{goalId:chapterId,stars:1|2|3},explanation?,source:"student"|"chapter"} => {submission}. POST /api/student/ack {version,chapterId} updates applied version + heartbeat. GET /api/sessions/:id/works => {learners,drafts,runs,submissions,feedback}; GET /api/learners/:id/works same filtered. POST /api/teacher/feedback {learnerId,chapterId,text}. GET /api/sessions/:id/export?format=json|csv|html. POST /api/teacher/recover {learnerId} => {recoveryCode}; POST /api/student/recover {recoveryCode,code?,deviceToken?} => session/learner. DELETE /api/sessions/:id teacher-only. GET /api/me => {role,session?,learner?}. POST /api/logout clears cookies.

### 第三章任务选择（v1.3.1）

`POST /api/student/task {taskId}` 允许在第三章已开放操作时选择 `rice-roll|tea|plant|fish`，使用学生 cookie 与 `X-Supermarket-Learner` 身份校验。返回完整课堂 state；`learner.taskId` 为当前选择，`learner.taskVersion` / `assignment.taskVersion` 每次换任务递增，同任务重复请求不递增。客户端忽略低版本的任务选择快照。其他章节、暂停或未开放操作时拒绝切换。

四个任务的草稿、运行和提交按学生、章节、任务分别保存，先前任务仍可离线补传；一个 draft ID 不得改成另一任务或章节。教师列表按作品任务筛选，详情可选择各任务，CSV 和打印导出分别包含已有任务作品。

### 学习自评（v1.3.2）

`LEARNING_GOALS` 为章节编号到学习目标文字的只读映射。学生提交界面为当前章节选择 1～3 星，未选不能提交；`selfAssessment:{goalId:chapterId,stars}` 随草稿版本、提交事务进入本机队列并补传。服务端校验 goalId 与作品章节一致、stars 为整数 1～3。重复 submissionId 保留初始提交内容，显式非法自评拒绝。

`source:chapter` 自动收存不产生自评；无自评字段的旧客户端提交仍可读取和补传，历史 explanation 保留。教师按学生、章节、任务展示最新有效学生自评与历次记录，未评单独显示，不计作 0 星。CSV 追加学习目标、最新自评星数和满分列，JSON 保留原始提交，打印包含自评记录。

### 教师演示（v1.3.3）

学生页左上角保留教师演示入口。`/?mode=demo` 在读取设备令牌、恢复学生身份或连接课堂前通过现有教师 Cookie 验证；未登录需输入后台密码。验证请求不发送学生角色头，双身份 Cookie 共存时仍可识别教师。演示使用独立 `teacher-demo` 本机存储作用域，不自动加入课堂、不连接学生事件流、不上传草稿、运行或自评，也不修改原 participant 或自动入场令牌。四个章节自由切换，第三章四任务分别保存；退出回到根地址后恢复正常学生课堂流程。未通过验证的占位画布不能保存。
