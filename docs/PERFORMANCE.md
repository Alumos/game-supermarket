# 课堂同步性能记录

2026-10-20，在 macOS / Node **v26.10.0** 本机回环网络测量。旧版为
`ff251f585bcc039bf9fb7d37f5bd9373cf1832a0`，修复版为本次同步与教师摘要优化后的工作区。
**这些数据用于定位软件开销，不是 Node 24 / Linux VPS 的容量或内存承诺。**

## 复现

```sh
node tests/load-profile.mjs --out /tmp/supermarket-profile.json
```

默认启动一个独立 Node 服务子进程，在临时目录新建 SQLite，绑定 `127.0.0.1` 随机端口；
创建 60 个模拟学生和一个教师 SSE 连接，再生成每人 50 条真实配送模拟运行与 50 条版本历史。
不读取或改写正式 `data/`，结束后停止子进程并删除临时数据库。
客户端与服务进程分离，报告中的 RSS / heap / CPU **只属于服务子进程**。
压测使用最多 64 个普通 HTTP 并发连接，SSE 连接另计。

可选参数：

```sh
# 快速检查，不生成历史
node tests/load-profile.mjs --history-runs 0
# 指向另一个完整源码目录中的服务，例如已解包的旧提交
node tests/load-profile.mjs --server /tmp/baseline/server.mjs --out /tmp/baseline-profile.json
# 额外观察临时服务在强制 GC 后的内存；仅用于诊断
node tests/load-profile.mjs --history-runs 10 --observe-gc
```

`--history-runs` 接受 0–100。基线完整历史接口会生成很大的响应，应在有余量的测试机器上复现。
脚本用旧版学生的“每收到 state 就 ACK”行为处理 SSE，以隔离服务端是否仍会产生级联广播；
它不是完整浏览器测试，不测教师 DOM 渲染、学生动画或实际校园网络。

## 60 人同时保存

同一脚本中，60 人各上传一次草稿，教师按 250ms 防抖读取一次作品。
SSE 字节数是实际响应正文，不含 HTTP / TLS 头。

| 指标 | 旧版 | 修复版 |
|---|---:|---:|
| 学生 state 事件 | 3,600 | 0 |
| 由上述事件产生的 ACK 请求 | 3,600 | 0 |
| 教师 state 事件 | 3,660 | 0 |
| 教师 works 事件 | 60 | 1 |
| SSE 正文 | 63,406,440 B | 48 B |
| 服务 CPU 时间 | 7,264 ms | 49 ms |
| SQLite `prepare()` 调用 | 706,569 | 5 |
| ACK 客户端延迟 P95 | 6,567 ms | 无级联 ACK |
| 本轮结束服务 RSS | 115.9 MiB | 32.7 MiB |

旧版一次学生保存会给全部学生广播课堂 state；每个学生随即 ACK；每次 ACK 又给教师发送完整学生列表。
因此“60 次保存”放大为 3,600 次 ACK，单次 ACK 处理约 2ms，排队后的客户端延迟却达到数秒。
教师端还会针对这些 state 重建界面，浏览器开销未计入上表。
修复版把作品变化通知合并给教师，课堂指令才广播学生；重复 ACK 通知被合并，SQL 语句复用。

额外对照：

| 操作 | 旧版 CPU / 教师 state | 修复版 CPU / 教师 state |
|---|---:|---:|
| 60 个显式心跳 GET + ACK | 150 ms / 60 | 29 ms / 1 |
| 教师一次暂停，60 人确认 | 161 ms / 61 | 41 ms / 2 |

暂停后的 ACK 客户端 P95 从 133ms 降至 17ms。
该心跳对照主动发送 60 个 ACK，未把新版学生 ACK 去重带来的额外减少计入收益。
60 个 SSE 保持静止约 1.58 秒，两版服务 CPU 均小于 1ms，且没有准备 SQL。

## 历史载荷

种子包含 **3,000 条真实配送运行、3,000 条版本历史**，其中运行 JSON 本身约 278.9 MB。
旧版忽略 `view=overview` 并返回完整作品；修复版由 SQL 仅投影教师概览所需字段。
两版测试的空增量均确保没有新作品。

| 指标 | 旧版完整作品 | 修复版教师概览 |
|---|---:|---:|
| 首次响应正文 | 283,211,242 B | 1,544,018 B |
| 首次服务 CPU | 2,419 ms | 916 ms |
| 首次客户端响应延迟 | 3,514 ms | 909 ms |
| 首次请求后服务 RSS / JS heap | 2,469 / 1,439 MiB | 42.9 / 10.4 MiB |
| 空增量正文 | 16,464 B | 16,479 B |
| 空增量服务 CPU | 2,255 ms | 4.2 ms |
| 空增量客户端响应延迟 | 1,715 ms | 2.9 ms |

旧版先读取、解析全部历史，再按 `since` 在 JavaScript 中过滤，导致“没有新作品”仍消耗大量 CPU 和临时内存。
修复版在 SQL 中按变化时间筛选，并避免把轨迹和完整结果读入概览的 JS 堆。
首次概览仍需 SQLite 处理已有运行 JSON，本次约 0.9 秒；数据继续增长时仍应观察首次打开延迟。
完整作品、导出和单个学生详情仍可能很大，这次优化没有删除或截断历史。

## 如何理解“空载约 300MB”

本机新进程启动时 RSS 约 22 MiB，60 个 SSE 连接时约 31 MiB；这些数值不能直接推算 Linux VPS。
进程曾经处理大 JSON 后，GC、V8 堆和底层分配器可能保留内存，之后没有用户也不必立刻回到启动值。
另一次旧版 600 条运行的诊断中，强制 GC 后 JS heap 约 7.7 MiB，但进程 RSS 仍约 281 MiB；
这提供了一种可复现解释，不能据此断言线上 283 MiB 的具体来源。

RSS、JS heap、容器内存统计和操作系统缓存含义不同；应结合线上进程、请求和数据库体积观察。
截图中 283 MiB / 1.93 GiB 本身没有显示内存耗尽，累计 CPU 时间也不是 CPU 使用率。
本次证据能确认请求放大、无效历史解析和教师重复刷新，不能证明 VPS 已经资源满载。

报告的各阶段包含等待异步通知稳定的时间，因此 `wallMs` 不应当成接口延迟；
接口延迟看 `clientLatencyMs` / `handlerP95Ms`，CPU 看子进程 `cpuMs`。
RSS 为阶段采样值，另有进程累计峰值字段；GC 时机、平台和数据库缓存会使重复测量有所波动。
